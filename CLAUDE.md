# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

Brainstorm is a knowledge-management product modeled as a desktop OS: an Electron shell that hosts sandboxed apps. The product anchors on **Block Protocol** (data interop), **Yjs** (CRDT), and **Lexical** (rich text). The design docs in `docs/` are the source of truth — read in order via [`docs/00-index.md`](docs/00-index.md). Action-oriented sequencing is in [`docs/implementation-plan.md`](docs/implementation-plan.md); unresolved design decisions are in [`docs/reference/11-open-questions.md`](docs/reference/11-open-questions.md) (referenced as `OQ-N`).

## Commands

```sh
bun install                    # install workspace deps
bun run dev                    # launch the shell (electron-vite dev, HMR)
bun run build                  # production build
bun run test                   # run all vitest suites
bun run test -- <path>         # run one file or pattern
bun run test:watch             # vitest in watch mode
bun run test:coverage          # coverage report (per-package floors enforced)
bun run typecheck              # tsc --noEmit across the workspace
bun run lint                   # biome check .
bun run format                 # biome format --write .
bun run size                   # size-limit budgets (per `.size-limit.json`)
bun run build:icons            # regenerate packages/shell/art/* from docs/art/icon/icon9.png
```

Workspace scripts proxy to `@brainstorm/shell` via `bun run --filter @brainstorm/shell <script>`. Dev tooling (biome, vitest, ts, vite) lives at the **root**; runtime deps (electron, react, @noble/*, yjs, better-sqlite3, @napi-rs/keyring) live in `packages/shell`. Don't add Electron/React deps at the root — that breaks the layering.

## Workspace layout (`packages/`)

- `shell/` — the Electron app: main process, preload, dashboard renderer, workers, all subsystems below.
- `tokens/` — `@brainstorm/tokens` (real). Semantic design tokens + themes.
- `sdk/`, `sdk-types/`, `react-yjs/`, `editor/`, `cli/` — placeholders. They get filled in across Stages 5/9/13 per the implementation plan; their `src/index.ts` currently exports `{}` with a comment pointing to the right stage.

## Big-picture architecture

**Three layers, two boundaries** (per [`docs/foundations/02-architecture.md`](docs/foundations/02-architecture.md)):

1. **Apps** — sandboxed renderers. Cross-app isolation is the security boundary; intra-app windows share a renderer (OQ-4 (b)).
2. **Shell** — Electron main process + privileged dashboard renderer. Owns the capability ledger, IPC broker, window manager, registry.
3. **Core services** — worker processes (`utilityProcess.fork`): storage worker, ydoc worker, search worker (later), sync worker (later).

**IPC envelope** (`packages/shell/src/ipc/envelope.ts`): every host-service call is a structured envelope `{v, msg, app, service, method, args, caps}`. The Broker (`ipc/broker.ts`) validates structure → verifies preload-stamped `app` against `RendererIdentityRegistry` (`ipc/renderer-identity.ts`) → checks capabilities against the per-vault `CapabilityLedger` → forwards to a service handler that ferries to a worker via `WorkerBridge`. **Fail-closed**: any throw from the capability check returns `Unavailable`, never approval. Each app has a fixed-depth pending queue; overflow drops oldest non-streaming requests (per-app backpressure, isolates from sibling apps).

**Vault session** (`main/vault/session.ts`): the in-memory state for an opened vault. Owns the keystore backend (keyring / passphrase / insecure-dev), the 32-byte master key (zeroed on dispose), the Ed25519 identity (private key never crosses IPC), the credential store, and the `DataStores` (4 SQLite DBs). Set/get/close via `setActiveVaultSession` / `getActiveVaultSession` / `closeActiveVaultSession`. The BrokerContext (`main/runtime/broker-context.ts`) bridges broker ↔ vault session: closures pass `verifyAppIdentity`, `checkCapability`, `onDenied` into the broker once at startup; the closures read from `getActiveVaultSession()` on every call.

**Storage** (`main/storage/`): runtime-agnostic `sqlite.ts` picks `bun:sqlite` under Bun (tests) and `better-sqlite3` under Electron (production). Four domain DBs: `ledger.db`, `registry.db`, `entities.db`, `search.db`. Each has its own migration list (`*-schema.ts`); migrations run inside a transaction and bump `_schema_version`. **Encryption-at-rest is deferred to Stage 3b** — the swap is one file (`sqlite.ts`) when the SQLCipher-capable driver lands. Yjs persistence is a snapshot+tail file format with per-update CRC32 (`ydoc-store.ts`); compaction at 256 KiB tail.

**Repository pattern for SQL** (Stage 5 decision): SQL strings never appear in feature code. Each table has a typed repo class under `main/storage/registry-repo/` (`apps`, `openers`, `blocks`, `entity_types`, `widgets`) and `main/capabilities/ledger.ts` for `capabilities`. Feature code (e.g. `AppInstaller`) is pure orchestration. If you find yourself wanting to write `db.prepare("INSERT INTO ...")` outside a repo, add a method to the repo instead.

**Workers**: `main/workers.ts` spawns `utilityProcess`-based workers (storage + ydoc) on app-ready, returns a `WorkersHandle` with the Broker and BrokerContext. The Broker's services are registered at startup; workers handle envelopes via `handle*Envelope` functions in `workers/<name>/index.ts` (testable in-process — the parentPort listener is gated on its presence so Vitest skips that block).

## Workflow standards (non-negotiable, per [`docs/implementation-plan.md`](docs/implementation-plan.md))

1. **New features ship with tests.** Coverage bar is the per-package floor in `docs/foundations/35-code-conventions.md` (85% shell core, 80% SDK, 70% first-party apps). CRDT code uses property tests; IPC envelopes round-trip through property tests; UI lands with Playwright assertions.
2. **Design, UX, performance are first-class.** No abstraction without three uses; no helper for one-shot ops. Every user-facing PR includes screenshot + keyboard path + screen-reader path + discoverability path. Any iteration touching a budget in [`12-shell-architecture.md`](docs/shell/12-shell-architecture.md) / [`13-frontend-stack.md`](docs/shell/13-frontend-stack.md) / [`18-storage-and-search.md`](docs/data/18-storage-and-search.md) ships before/after numbers. `size-limit` budgets are enforced.
3. **Continuous audits.** Every PR gets a security review (new capability surface? new IPC method? new dependency?). Stage boundaries trigger three audits (stability + performance + security) recorded under `docs/_review/<date>-stage-<n>-audit.md`. The `review` and `security-review` skills exist for this.
4. **Reproduce before you patch; verify what's running before you conclude.** A bug that can be hit in any vault is reproducible in the in-process pipeline — add/extend a test in `packages/shell/src/main/integration/app-data-pipeline.test.ts` (or the relevant `*-service.test.ts`) and watch it fail *first*. Never enter a "patch → ask the user to retest" loop. Before concluding a fix "didn't work", confirm the build is actually running: every app logs `[app:<id>] build <sha>` in its own DevTools console and the shell logs `[shell] launch … build <sha>` / `[seed] reinstalled … build <sha>`; if those shas don't match (or are old) the shell wasn't restarted — **apps only re-deploy into the running shell on a full shell restart** (the dev seeder rebuilds+reinstalls first-party apps on boot; reloading a window serves the stale vault copy). `bun run verify` (typecheck + build apps + in-process pipeline/entities tests) is the pre-handoff gate for any shell/app data-path change.
5. **Dogfood-surfaced *features* get a plan rung the same turn they ship.** `docs/dogfood/friction-log.md` is the channel for bugs / design nits / gaps (triage + fix in place). But a dogfood session that ships a genuinely **new feature** — a new affordance, a cross-app capability, a shared SDK primitive — must also land a tracked iteration id in `docs/implementation-plan.md` that same turn (✅ with its commit[s]), not live only in the friction log. The plan is the source of truth for *what exists*; a shipped feature the plan can't see is a divergence (the read-only-lock fleet, shared `<EmptyState>`, and inline-toolbar polish were retro-filed 2026-06-28 because this rule was missing). A bug fix is not a feature — the test is "would a user call this a new thing the product can now do?"

## Stage gating (how to think about progress)

Work proceeds through the 14 stages in `docs/implementation-plan.md`. Each stage has **blocking OQs** that must be resolved (a position taken, documented in `11-open-questions.md`) before code lands. **Stages 0–13 are essentially DONE — the public beta `v0.1.5` shipped 2026-06-29** (signed + notarized macOS, Windows, Linux on GitHub Releases, with in-app auto-update). What remains is **GA polish** (a11y/perf tails, Windows EV signing, vector/embedding search) and the **v2 commercial/multi-user stack** (Stage 14). Don't start a stage's iterations without resolving its OQs first. When an OQ is resolved during a stage, mark it `*[RESOLVED in implementation-plan Stage N]*` in `11-open-questions.md` and note the resolution in the plan's stage section.

**Update the implementation plan in the same turn an iteration lands** (this is a workflow rule, not aspirational): mark the iteration ✓ DONE with a one-line note on what changed; update the status snapshot; note OQs resolved.

## Conventions that bite

- **File naming**: `kebab-case` for files and folders (per `35-code-conventions.md`). React components / types are `PascalCase`; functions / vars are `camelCase`.
- **No default exports** for library code (named exports only). Config files (`*.config.ts`) are exempted via `biome.json` override.
- **No `import type` for runtime values**; use `import type` where appropriate. Strict TS + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`. **The `apps/*` typecheck must run separately from the workspace one.** Vite/esbuild *strips* a type-only import — `import { type Foo }` then `Foo.bar()` makes `Foo` `undefined` at runtime and throws, with **zero** build/typecheck signal from `tsc --noEmit` on the workspace `tsconfig.json` (which only includes `packages/*/src`). This exact bug — `type Texture` then `Texture.from()` — silently killed all Graph icons and was "fixed" blind 5×. `bun run typecheck` now chains `typecheck:packages` *and* `typecheck:apps` so the canonical command catches it; if you only want one half, call those scripts directly.
- **No comments explaining WHAT** — code reads itself. Comments only when the WHY is non-obvious (a workaround, a constraint, a security invariant). No "removed X" placeholders; delete the code.
- **Crypto routing**: only `main/credentials/` may import `@napi-rs/keyring` or platform keystore APIs. Apps and other code call through the credential store. Same shape will apply to AI provider keys in Stage 11.
- **No inline SQL outside repos.** See "Repository pattern for SQL" above.
- **No raw string literals as discriminators — use enums.** Anywhere a string is a `kind`, `mode`, `status`, `verb`, or any other value drawn from a known small set, declare a TS string enum (or `const X = { ... } as const` with a derived union type if you need to avoid enum runtime emission) and reference it by name everywhere. `case "solid":` is rejected — use `case WallpaperKind.Solid:`. Wire format stays as strings because the enum values *are* strings. Centralising the literal makes refactors / search / grep tractable and stops typos compiling. Existing string-literal unions (`DashboardIconKind`, opener kinds, etc.) are tech debt to migrate as adjacent code is touched.
- **No phantom CSS tokens — only reference custom properties that exist.** Every `var(--x)` in app-side CSS must name a real theme token (`packages/tokens`, flattened as `--color-…`/`--space-…`/`--radius-…`), an app-theme alias (`packages/sdk/src/app-theme.css`: `--text`, `--bg-elev`, `--hover`, …), or a var the code itself declares/injects. A made-up name "works" in the theme you eyeballed because the `var(--nope, fallback)` fallback renders — then breaks silently on every other theme (the comments panel shipped unreadable-on-dark exactly this way: phantom `--color-text-subtle` & co. collapsing to light-theme rgba fallbacks). If the design genuinely needs a new token, add it to **every** theme in `packages/tokens/src/themes.ts` first, then use it. Enforced by `tools/check-css-tokens.mjs` in `bun run lint` / `verify` (zero-baseline — it fails on any unknown name).
- **Keyboard via the shortcut registry, never raw `e.key`.** Per [`docs/foundations/35-code-conventions.md §Keyboard handling`](docs/foundations/35-code-conventions.md). Use the renderer-side `useShortcut(id, handler)` hook (and declare new ids in `renderer/shortcuts/default-chords.ts` mirroring the main-process registry). Even trivial keys like `Escape` get an action id.
- **Every user-visible string wraps in `t(key)`.** Per [`docs/foundations/35-code-conventions.md §Localization`](docs/foundations/35-code-conventions.md). No bare JSX text. Add new ids + their English source to `renderer/i18n/en.json` (the FormatJS/ICU source-language catalog `t()` loads, since 12.1). **Two `t()`s, two plural rules — don't mix them.** (1) The **shell renderer** `t()` is FormatJS/ICU: plurals use ICU (`{count, plural, one {…} other {…}}`), never a `count === 1 ?` branch in component code. (2) Each **sandboxed app** uses the lighter `createT` from `@brainstorm/sdk/i18n`, which does **`{name}` interpolation only — NO ICU** (so an app needn't bundle a formatter). An ICU plural string written against `createT` leaks the raw `{count, plural, …}` template to the UI (this bit automations + browser — F-162). App-side plurals go through the shared **`plural(t, count, "<base>.one", "<base>.other")`** helper with two `{count}`-style catalog keys; the `count === 1` selection lives inside that helper (the sanctioned place), never in component code. Re-export a catalog-bound `plural` from the app's `i18n.ts` (see `apps/automations/src/i18n.ts`).
- **Popovers / dialogs use the shared `<Popover>` primitive** from `renderer/ui/` so backdrops, panels, headers, close affordances and shadows are consistent. No per-component dialog chrome.
- **Panel headers share a fixed height (44px) and a 1px subtle bottom border.** Whenever a surface has multiple stacked panels (e.g. Settings sidebar + main, future multi-pane app windows), every panel's header sits on the same horizontal baseline. The shared `.dashboard__header` / `.settings__main-header` / `.settings__sidebar-header` rules in the renderer CSS already encode this — when adding a new panel, mirror them (44px, `border-bottom: 1px solid var(--color-border-subtle)`, no top padding) rather than inventing a new chrome.
- **The app `.app-header` chrome is owned entirely by `@brainstorm/sdk/app-theme.css` — never re-declare it per app.** The shared `:root .app-header` rule provides the flex skeleton (`display:flex` / `space-between` / `gap` / `flex-shrink:0`), the bottom border, the GLASS surface (every app's header is glass — there are no surface modifiers; `app-header--glass`/`--chrome` are gone), the drag region, and (with `app-header__left/__right/__title`) the left/right groups + the title face (size / weight / colour / ellipsis / `max-width: min(440px, 60vw)` / `margin:0`). Put the class `app-header__title` on the title element in EVERY app — a per-app re-creation of the title face (a `.x__header-title` with its own font rules) is rejected; that fork is exactly how Preview shipped a medium-weight title and Graph a 12px dim one. Height + platform padding come from `app-preload.ts`. An app supplies only genuinely-unique deltas (Graph's absolute overlay positioning, Calendar's `.app-header__right { flex:0 0 auto }`, Browser's tab-strip `justify-content`/`gap`/`overflow-x` — note app-side `.app-header` overrides need `:root`-level specificity to beat the SDK rule). A per-app `.app-header { display:flex; … }` copy is rejected: that drift is exactly what let Mailbox ship a header missing `margin:0` (title blew out the 44px baseline). Notes still styles its header *children* via its own `.notes__header-left/right` classes — the one allowed namespace exception (its title carries the shared `app-header__title`).
- **The header object-menu ⋯ is the LAST (rightmost) element in `.app-header__right`.** Every app's header right group reads identically: content actions and panel toggles first, the object ⋯ menu last. The ⋯ is the catch-all overflow — it anchors the trailing edge so it's in the same spot in every app. Notes / Journal / Database already do this; mirror their order (e.g. open-original → sidebar toggle → inspector toggle → ⋯). The right-click trigger stays on the title (never the ⋯ on the title). Pairs with the SDK menu-anchoring rule below.
- **A right-panel toggle must declare whether it can act — an enabled button that does nothing is rejected.** Build every sidebar/inspector toggle with the shared `@brainstorm-os/sdk/panel-toggle` (`<PanelToggleButton>` React / `createPanelToggleButton` DOM); `panelToggleIcon` is the helper's private glyph, not an app-facing export. A `PanelSide.Right` toggle whose panel only renders with a selection passes **`disabled` *and* a `hint`** naming what to select first (a disabled control fires no pointer events, so the tooltip chip can't open — the native `title` is the only explanation the user gets). The alternatives are to make the panel always live (its own empty state, or a CSS collapse) and baseline the file, or to seed a selection on open (Database). **Conditionally rendering the toggle is rejected** — the control vanishes, the header jitters, and the panel becomes undiscoverable. Enforced by `tools/check-panel-toggles.mjs` in `bun run lint`; the reasoning + the per-app table are in [apps/09-shared-sdk-catalog.md §Panel-toggle availability](docs/apps/09-shared-sdk-catalog.md).
- **A cover host inside a column flex panel gets `flex-shrink: 0`.** The entity cover band (`@brainstorm/sdk/entity-cover`) has *no* explicit height — it's purely `aspect-ratio × width`. Every right-panel inspector body is a `display: flex; flex-direction: column` scroll container, so its default `flex-shrink: 1` compresses the band to make room for the other properties — the cover then renders at a *different* height per object depending on how much else it has (the symptom: "cover height jumps between objects"). The cover element pins itself for the direct-mount case, but consumers wrap it in their own clickable host (`.db-inspector__cover` button, `.inspector__preview-cover` div, cover-picker's `.cover-picker__preview`) and *that* host is the real flex item — so the host's CSS rule must carry `flex-shrink: 0`. Apply it the moment you drop a cover into any inspector/right panel, not as a follow-up fix.
- **Click-anchored menus pass an anchor `element` (or `rect`) for tracking; a per-open `position` override is also honored (since `@react-fancy-menus/core` 0.2.0).** Open the shared menu through `openObjectMenu` / `openAnchoredMenu(point, …, { anchor })` / `openContextMenu(point, …, { anchor })`. **Default to an anchor `element`/`rect`** — the runtime positions off it *and* keeps the menu tracking via Floating UI autoUpdate (flip + shift off the live rect); fixed coordinates don't track. `OpenParam.position` (a `Partial<PositionConfig>`) is now **shallow-merged over the static `config.position` at open time, per-key win** — use it to re-align ONE registered config without a config-per-variant. ⚠️ Earlier versions (≤0.1.0) *ignored* per-open `position` and silently centred the menu on the viewport — that was the reason for the old "never `fixedX/fixedY`" rule; it no longer holds, but still reach for `fixedX/fixedY` only when you genuinely have no anchor element and want no tracking. Rules: (1) **button-triggered** menus pass the trigger `element` so the menu follows + flips + shifts off the live rect; (2) a **right-positioned** trigger (the object-menu ⋯, header buttons) right-aligns (`MenuAlign.End`) so the menu's right edge sticks to the button's right edge instead of drifting left — `openObjectMenu` defaults ⋯ to End; left chips/cursor menus stay `Start`; (3) passing an `anchor` element also toggles `aria-expanded="true"` on it for the open/active state (`.bs-object-menu__more[aria-expanded="true"]` styling). Right-click menus pass the cursor point (collapsed rect, no anchor). Per-open `ariaLabel` (`OpenParam.ariaLabel`, 0.2.0) gives one config many distinct screen-reader names. **Host-driven editor typeaheads** (slash `/`-menu, `@`-mention, emoji) keep editor focus via **controlled-list mode** — `ListBody.focusOnMount: false` + a per-open `activeIndex` + `keyboard.navigation: KeyboardNavigation.None` (0.2.0) — the sanctioned replacement for the current bespoke-`<div>` typeahead workaround in `packages/editor/src/plugins/*` (migration pending; these are the one standing exception to the "every menu uses the shared runtime" rule below).
- **Every menu / dropdown / context-menu uses the shared fancy-menus runtime — no bespoke menu chrome, ever.** Mount the runtime once per app (`mountMenuHost()` from `@brainstorm/sdk/menus`) and open EVERY menu through the shared openers (`openObjectMenu` / `openAnchoredMenu` / `openContextMenu`) — object ⋯ menus, header overflow menus, view/sort/filter dropdowns, slash-command pickers, right-click context menus, and any "pick one of N" popup. A hand-rolled `<div>`/`<select>`/absolutely-positioned list standing in for a menu is rejected: it drifts from the shared keyboard model, anchoring, theming, and a11y. (Anchoring mechanics for these are the next bullet.) This is a standing rule for new code and rewrites alike. *The one current exception* — the `packages/editor` host-driven typeaheads (slash `/`-menu, `@`-mention, emoji), which hand-roll a list because ≤0.1.0's list body auto-focused and froze the editor caret — is now migratable onto the runtime via 0.2.0 controlled-list mode (prior bullet) and should be converted, not extended. **Native `<select>` is rejected too** — enumerated choices render through `@brainstorm/sdk/select-menu` (`<SelectMenu>` React / `createSelectMenu` DOM / `openSelectMenu` imperative): a `.bs-select` trigger opening its options as a fancy menu, check on the chosen option, `group` for the `<optgroup>` case.
- **File-open / file-save dialogs declare allowed extensions when the operation is filterable.** Every `dialog.showOpenDialog(...)` / `dialog.showSaveDialog(...)` that targets a specific kind of content passes `filters: [{ name: "<kind>", extensions: [...] }]`. The kind name is t-translatable; the extensions list is exhaustive for what the consuming feature can actually handle. Wallpaper upload uses `["png", "jpg", "jpeg", "webp", "gif", "avif"]`; vault-folder pickers correctly don't (they pick directories, not files).
- **DRY everywhere — extract before you copy.** Two call sites doing similar things go through the same helper / component / hook. Three is a hard ceiling. Visible places this already applies: `<Popover>`, `<Icon>`, `t()`, `useShortcut()`, the panel-header CSS pattern. A PR that copy-pastes UI chrome instead of using the shared primitive is rejected.
- **Reuse the SDK — check the catalog before writing any component.** `@brainstorm/sdk` is the reusable library every app builds on. **Before writing a component / helper / list row / popover / formatter / picker / icon / data-access layer, read [`docs/apps/09-shared-sdk-catalog.md`](docs/apps/09-shared-sdk-catalog.md) and `packages/sdk/package.json`'s `exports` map** — if it exists, import it from its documented subpath; if it exists in one app and you need it in a second, extract it to the SDK (CSS included, as a subpath export) rather than copying. Over-extraction is also a smell — the catalog's *What is deliberately not shared* lists the app-specific adapters that correctly stay local.
- **Reactive apps use React + the ONE shared reactivity stack — never a hand-rolled change loop.** A reactive app (anything backed by vault/Yjs entities that updates from other devices/users — nearly every app, code-editor included) reads live state ONLY through `@brainstorm/react-yjs`: the Yjs document body via `useYMap`/`useYText`/`useYDoc`, and live entity lists via `useVaultEntities` / `useLiveEntities` (over the pure `createQueryStore`). **Do NOT write `vaultEntities.onChange → list() → setState/render`** — that re-implements the reactivity layer per app (the drift that caused the bookmarks scroll-blink + a different coalescer in every app). Enforced by `tools/check-app-reactivity.mjs` (a shrinking baseline ratchet in `bun run lint`/`verify`): new code using the raw signal fails CI. Scaffold a compliant React app with `bun run new-app <id> "<Name>"` (React root + `.app-header` + a live `useVaultEntities` list). **EVERY app is a React app — this is a hard standing rule: no app (new or existing) ships imperative-DOM `app.ts` chrome.** Canvas-heavy apps (Graph, Whiteboard) confine imperative code to the draw loop itself behind a ref boundary and build all surrounding chrome (header, sidebars, panels, dialogs, menus) in React. The imperative-DOM first-party apps are being migrated to React on the all-apps-React track (theme-editor 9.9.7 · graph 9.13.16 · calendar 9.15.22 · whiteboard 9.17.21 · automations 11b.17 · preview 9.20.12); `apps/theme-editor` (9.9.7) is the reference conversion (the original `apps/github-issues` reference was removed 2026-06-11 — Mailbox is the connector-framework reference now). Per [`docs/shell/13-frontend-stack.md §Decision`](docs/shell/13-frontend-stack.md).
- **Imperative DOM mounted into a React tree (the hybrid `useDomHost`/`replaceChildren` pattern) must sit in a `key`ed or single-owner slot — never as one of two same-type branches React reconciles in place.** When a hybrid app appends content React doesn't own (`slot.replaceChildren(view.root)` for a DOM-built surface), React has no idea that subtree exists and will not remove it on a re-render. The trap: a `{cond ? <div className="x"/> : <div className="x">…</div>}` ternary where both branches are the *same element type at the same position* — React reuses the one DOM node across the flip and leaves the imperatively-injected child orphaned *on top of* the new branch's content. Symptom: navigation/state updates correctly (the ground-truth `data-*` attr flips) but a stale view stays painted, so the screen looks frozen. This is exactly how Tasks shipped "open a task → can't navigate anywhere" — the closed task's `.tasks-detail` node lingered over the list (fixed by giving each ternary branch a distinct `key` so React unmounts the node + its foreign children). Rule: give the two branches distinct `key`s (forces unmount/remount), OR mount all imperative content through ONE stable slot you clear yourself, OR — best — finish the React conversion so the content is real JSX React owns. The underlying lesson: every `replaceChildren` into a React-rendered host is a reconciliation footgun; the fix-class is fewer hybrids, not more keys.
- **`@noble/*` imports require the `.js` suffix** (`@noble/hashes/argon2.js`, `@noble/ciphers/chacha.js`, `@noble/curves/ed25519.js`). The package `exports` map requires it.
- **`bun:sqlite` is dynamically imported** behind `typeof Bun !== "undefined"` so the non-Bun build (Electron) typechecks. The import specifier is intentionally opaque to TS.

## Multi-agent orchestration (claim → work → hand off)

When more than one agent works the repo in parallel, coordinate through the dev MCP server's lease ledger — **never** race on shared files or reconcile by hand. The ledger lives under the git common dir, so every git worktree of the repo sees the same state. Protocol:

1. **`orchestration.status`** first — see who owns what before picking up work.
2. **`orchestration.claim`** `{ task, owner, worktree, branch }` before touching a task (`task` = a plan iteration id like `9.13.5`). A claim on an actively-held task **fails closed** with conflict detail; pick something else or coordinate. Work in an isolated git worktree (the Agent tool's `isolation: "worktree"`), not the shared tree.
3. **`orchestration.renew`** periodically during long work so the lease isn't reaped as stale (default TTL 30 min).
4. **`orchestration.handoff`** `{ done, remaining, files, verify }` if you stop before finishing — the next agent inherits this payload via **`orchestration.resume`** instead of reconstructing state. **`orchestration.release`** when the task is done.
5. Only a single designated integrator merges completed branches to `main`; parallel agents never write `main` directly.

This is dev-process state only — it never lives under `docs/`. A2A and other cross-vendor agent protocols are explicitly out of scope: there is no non-Claude-agent interop need.

**Gates are recorded, not asserted (per [`docs/foundations/70-graph-engineering.md`](docs/foundations/70-graph-engineering.md)).** When a rung goes ✅ behind a gate — `/security-review`, `/pentester`, a packaging dry-run, a perf pass — append the run to [`docs/_review/evaluations.jsonl`](docs/_review/evaluations.jsonl) (`{rung, gate, verdict, rubric, evidence, date}`) and declare it on the plan bullet as `` `<gates: …>` ``. `plan-gate-check` then makes ✅ **unreachable** while a declared gate has no passing, rubric-bearing run — and the *latest* run decides, so a later failure un-blesses the rung. **A failed run is never edited or deleted; you supersede it by appending a pass.** This exists because a PR was opened claiming "both gates run" while a pentest was still executing, and it came back with three blocking findings — one a remotely-reachable uncaught exception. A verdict with no rubric is rejected, because that is exactly the shape a premature claim takes.
